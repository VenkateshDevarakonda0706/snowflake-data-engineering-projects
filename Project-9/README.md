# Project 9 — Customer History Management using SCD Type 1 and Type 2

## 📌 Project Overview

This project demonstrates **Slowly Changing Dimensions (SCD)** in Snowflake using two approaches:

- **SCD Type 1** — overwrites changed customer information.
- **SCD Type 2** — preserves historical customer versions.

The project uses an online retail customer scenario where attributes such as **city, state, membership, and segment** can change over time.

---

## 🎯 Objectives

The main objectives of this project are to:

- Create a Snowflake database and schema.
- Load customer data from CSV files.
- Implement an SCD Type 1 customer dimension.
- Demonstrate Type 1 history loss.
- Implement an SCD Type 2 customer dimension.
- Preserve historical customer versions.
- Use effective and expiry dates.
- Identify current records using `IS_CURRENT`.
- Perform historical date-based analysis.
- Compare SCD Type 1 and SCD Type 2.
- Validate the final record counts.

## 🔄 SCD Type 1

SCD Type 1 is used when historical values are not required.

When a customer changes:

```text
Old value
   ↓
Overwritten
   ↓
Current value
```

### Type 1 Characteristics

| Feature | Type 1 |
|---|---|
| Old value preserved | ❌ No |
| New row created | ❌ No |
| Historical analysis | ❌ No |
| Effective date | ❌ No |
| Expiry date | ❌ No |
| `IS_CURRENT` | ❌ No |
| Storage | Lower |

### Example

Customer 101:

```text
Before:
Hyderabad | Telangana | Silver

After:
Bengaluru | Karnataka | Gold
```

The original values are no longer available in the Type 1 dimension.

---

## 🕒 SCD Type 2

SCD Type 2 is used when complete customer history must be preserved.

When a customer changes:

```text
Existing record
      ↓
Expire old version
      ↓
Insert new version
```

### Type 2 Columns

| Column | Purpose |
|---|---|
| `CUSTOMER_KEY` | Surrogate key |
| `CUSTOMER_ID` | Natural/business key |
| `CUSTOMER_NAME` | Customer name |
| `CITY` | Customer city |
| `STATE` | Customer state |
| `MEMBERSHIP` | Membership |
| `SEGMENT` | Customer segment |
| `EFFECTIVE_DATE` | Beginning of version |
| `EXPIRY_DATE` | End of version |
| `IS_CURRENT` | Current-record indicator |

### Type 2 Characteristics

| Feature | Type 2 |
|---|---|
| Old value preserved | ✅ Yes |
| New row created | ✅ Yes |
| Historical analysis | ✅ Yes |
| Effective date | ✅ Yes |
| Expiry date | ✅ Yes |
| `IS_CURRENT` | ✅ Yes |
| Storage | Higher |

New version:

```text
Current:   TRUE
```

The old version remains available for historical analysis.

---

## 🔑 Surrogate Key vs Natural Key

### `CUSTOMER_ID`

This is the natural/business key supplied by the source system.

Example:

```text
101
102
103
```

### `CUSTOMER_KEY`

This is the surrogate key generated by Snowflake.

A single customer can have multiple Type 2 records, and each version can have a different surrogate key.

The surrogate key is **not required to be gap-free or sequential**.

---

## 📊 Historical Analysis

Type 2 makes it possible to answer historical questions.

Example:

> What was Customer 101's membership on March 15, 2026?

The historical record is found using:

```sql
requested_date BETWEEN EFFECTIVE_DATE AND EXPIRY_DATE
```

For March 15, 2026:

```text
Customer 101
Membership → Silver
City       → Hyderabad
```

This information would not be available from the Type 1 table after the update.

## ⚖️ Type 1 vs Type 2 Summary

```text
                 SCD TYPE 1       SCD TYPE 2
------------------------------------------------
Old value        Overwritten      Preserved
New row          No               Yes
History          No               Yes
Effective Date   No               Yes
Expiry Date      No               Yes
IS_CURRENT       No               Yes
Storage          Lower            Higher
```

### Simple way to remember

```text
TYPE 1 → Keep latest value

TYPE 2 → Keep complete history
```
