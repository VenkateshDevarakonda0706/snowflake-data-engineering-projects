# Project 8 — Customer Profile History Analysis using Snowflake

## 1. Project Overview

### Project Name
**Customer Profile History Analysis using Snowflake**

### Main Concept
**Slowly Changing Dimension (SCD) — The Problem**

This project demonstrates the Slowly Changing Dimension problem in a Snowflake data warehouse.

An online retail company maintains customer information such as:

- City
- State
- Membership
- Customer Segment

These attributes can change over time.

For example, Customer 101 initially lives in Hyderabad and has Silver membership. Later, the customer moves to Bengaluru and upgrades to Gold membership.

If the existing dimension row is simply updated, the previous values are overwritten and historical information is lost.

The project demonstrates this problem before deciding how historical changes should be handled.

# 5. Task 2 — Create Initial Customer Dimension

The initial customer dimension was created as:

```sql
CREATE OR REPLACE TABLE DIM_CUSTOMER
(
    CUSTOMER_KEY NUMBER AUTOINCREMENT,
    CUSTOMER_ID NUMBER,
    CUSTOMER_NAME VARCHAR(100),
    CITY VARCHAR(100),
    STATE VARCHAR(100),
    MEMBERSHIP VARCHAR(50),
    SEGMENT VARCHAR(50)
);
```

## Column Explanation

| Column | Purpose |
|---|---|
| `CUSTOMER_KEY` | Warehouse surrogate key generated by Snowflake |
| `CUSTOMER_ID` | Source/business customer identifier |
| `CUSTOMER_NAME` | Customer name |
| `CITY` | Customer city |
| `STATE` | Customer state |
| `MEMBERSHIP` | Customer membership level |
| `SEGMENT` | Customer segment |

`CUSTOMER_KEY` is generated automatically using `AUTOINCREMENT`.

The source `CUSTOMER_ID` remains the business identifier.

# 9. Task 6 — Identify Changed Customers

The next step was to compare the current dimension with the incoming updates.

The attributes compared were:

- City
- State
- Membership
- Segment

SQL:

```sql
SELECT
    d.CUSTOMER_ID,
    d.CITY AS OLD_CITY,
    u.CITY AS NEW_CITY,
    d.MEMBERSHIP AS OLD_MEMBERSHIP,
    u.MEMBERSHIP AS NEW_MEMBERSHIP
FROM DIM_CUSTOMER d
INNER JOIN CUSTOMER_UPDATES u
    ON d.CUSTOMER_ID = u.CUSTOMER_ID
WHERE
       d.CITY <> u.CITY
    OR d.STATE <> u.STATE
    OR d.MEMBERSHIP <> u.MEMBERSHIP
    OR d.SEGMENT <> u.SEGMENT
ORDER BY d.CUSTOMER_ID;
```

Expected result:

| Customer ID | Old City | New City | Old Membership | New Membership |
|---|---|---|---|---|
| 101 | Hyderabad | Bengaluru | Silver | Gold |
| 103 | Vijayawada | Chennai | Silver | Gold |
| 104 | Hyderabad | Hyderabad | Gold | Platinum |

This identifies the customers whose attributes have changed.

# 10. Task 7 — Identify Attribute Changes

Task 7 identifies the exact attributes that changed.

SQL:

```sql
SELECT
    d.CUSTOMER_ID,
    'CITY' AS ATTRIBUTE,
    d.CITY AS OLD_VALUE,
    u.CITY AS NEW_VALUE
FROM DIM_CUSTOMER d
JOIN CUSTOMER_UPDATES u
    ON d.CUSTOMER_ID = u.CUSTOMER_ID
WHERE d.CITY <> u.CITY

UNION ALL

SELECT
    d.CUSTOMER_ID,
    'STATE' AS ATTRIBUTE,
    d.STATE AS OLD_VALUE,
    u.STATE AS NEW_VALUE
FROM DIM_CUSTOMER d
JOIN CUSTOMER_UPDATES u
    ON d.CUSTOMER_ID = u.CUSTOMER_ID
WHERE d.STATE <> u.STATE

UNION ALL

SELECT
    d.CUSTOMER_ID,
    'MEMBERSHIP' AS ATTRIBUTE,
    d.MEMBERSHIP AS OLD_VALUE,
    u.MEMBERSHIP AS NEW_VALUE
FROM DIM_CUSTOMER d
JOIN CUSTOMER_UPDATES u
    ON d.CUSTOMER_ID = u.CUSTOMER_ID
WHERE d.MEMBERSHIP <> u.MEMBERSHIP

UNION ALL

SELECT
    d.CUSTOMER_ID,
    'SEGMENT' AS ATTRIBUTE,
    d.SEGMENT AS OLD_VALUE,
    u.SEGMENT AS NEW_VALUE
FROM DIM_CUSTOMER d
JOIN CUSTOMER_UPDATES u
    ON d.CUSTOMER_ID = u.CUSTOMER_ID
WHERE d.SEGMENT <> u.SEGMENT

ORDER BY CUSTOMER_ID, ATTRIBUTE;
```

Expected result:

| Customer ID | Attribute | Old Value | New Value |
|---|---|---|---|
| 101 | CITY | Hyderabad | Bengaluru |
| 101 | STATE | Telangana | Karnataka |
| 101 | MEMBERSHIP | Silver | Gold |
| 103 | CITY | Vijayawada | Chennai |
| 103 | STATE | Andhra Pradesh | Tamil Nadu |
| 103 | MEMBERSHIP | Silver | Gold |
| 104 | MEMBERSHIP | Gold | Platinum |

This is the core change report.

# 11. Task 8 — Demonstrate the SCD Problem

The project intentionally demonstrates the current approach where the existing dimension record is overwritten.

The update was performed using:

```sql
UPDATE DIM_CUSTOMER d
SET
    CUSTOMER_NAME = u.CUSTOMER_NAME,
    CITY          = u.CITY,
    STATE         = u.STATE,
    MEMBERSHIP    = u.MEMBERSHIP,
    SEGMENT       = u.SEGMENT
FROM CUSTOMER_UPDATES u
WHERE d.CUSTOMER_ID = u.CUSTOMER_ID;
```

Three existing customer records were updated:

```text
101
103
104
```

The important point is that the old dimension values were replaced.

For Customer 101:

```text
Before:

101 → Hyderabad → Telangana → Silver

After:

101 → Bengaluru → Karnataka → Gold
```

The existing row now contains only the latest values.

# 13. Task 10 — Demonstrate Historical Data Loss

The project specifically asks whether the current dimension can tell us where Customer 101 lived before the update.

Query:

```sql
SELECT
    CUSTOMER_ID,
    CUSTOMER_NAME,
    CITY,
    STATE,
    MEMBERSHIP
FROM DIM_CUSTOMER
WHERE CUSTOMER_ID = 101;
```

Current result:

| Customer ID | Customer Name | City | State | Membership |
|---|---|---|---|---|
| 101 | Amit Sharma | Bengaluru | Karnataka | Gold |

However, the original information was:

```text
City       = Hyderabad
State      = Telangana
Membership = Silver
```

That information has disappeared from the current dimension row.

Therefore, using only the current `DIM_CUSTOMER`, the company cannot determine the customer's previous city, state, or membership.

# 15. Overall SCD Problem

The project demonstrates the following pattern:

```text
                 Customer Change
                       |
                       v
              Existing Dimension
                       |
                       v
                   UPDATE
                       |
                       v
              Old Values Replaced
                       |
                       v
             Historical Data Lost
```

The current design keeps one row per customer.

Therefore:

```text
One Customer
     |
     └── One Dimension Row
              |
              └── UPDATE
                    |
                    └── Old Version Lost
```

This is the Slowly Changing Dimension problem demonstrated in Project 8.

# 16. Key Concepts Learned

## 16.1 Business Key

`CUSTOMER_ID` represents the source/business customer identifier.

Example:

```text
CUSTOMER_ID = 101
```

It identifies the same real-world customer even when customer attributes change.

## 16.2 Surrogate Key

`CUSTOMER_KEY` is the warehouse-generated key.

It was created as:

```sql
CUSTOMER_KEY NUMBER AUTOINCREMENT
```

The project uses it as the warehouse key for the customer dimension.

## 16.3 Dimension Attribute Change

Customer attributes can change over time.

Examples:

```text
Hyderabad → Bengaluru
Silver → Gold
Gold → Platinum
```

## 16.4 Overwrite Problem

If the existing dimension row is simply updated, the previous value is no longer available in the dimension.

## 16.5 Historical Data Loss

Because the old values are overwritten, historical analysis cannot be performed using the current dimension alone.

---

# 17. Final Project Conclusion

Project 8 demonstrates why customer dimensions require a strategy for handling changing attributes.

The project does not implement a historical SCD solution. Instead, it first demonstrates the problem:

```text
Initial Customer Data
        ↓
Customer Updates
        ↓
Identify Changes
        ↓
Overwrite Dimension
        ↓
Historical Values Lost
```

For Customer 101:

```text
Hyderabad → Bengaluru
Telangana → Karnataka
Silver → Gold
```

After the overwrite, only the new values remain in `DIM_CUSTOMER`.

Therefore, when a business needs to analyze both current and historical customer information, simply overwriting dimension records is not sufficient.

This completes Project 8 — Customer Profile History Analysis using Snowflake.
