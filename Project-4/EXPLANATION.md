# Project 4 — Retail Sales Data Warehouse

## 1. Project Overview

This project implements a Retail Sales Data Warehouse using Snowflake and a Star Schema dimensional model.

The goal is to transform retail sales source data stored in CSV files into a structured analytical data warehouse that can answer business questions such as:

- How much revenue did each customer generate?
- Which products generate the most revenue?
- Which branches perform best?
- How much revenue was generated by each month?
- Which states generate the most revenue?
- Which product categories perform best?
- Who are the top customers?
- What are the top products?
- How are sales changing over time?
- Which regions generate the most revenue?
- How does revenue vary by quarter?

The project demonstrates the complete flow from raw source data to analytical reporting.

---

# 2. Business Process

## Business Process: Retail Sales Analytics

The business process being analyzed is:

> Retail Sales Analytics

The company wants to analyze the sales transactions generated when customers purchase products from different branches.

The warehouse is therefore designed around the retail sales business process.

---

# 3. Business Event

A business event is something that actually happens in the business.

For this project, the business event is:

> A customer purchases a product from a branch on a specific date.

Example:

```text
Customer 1 purchases Product 101
from Branch 1
on Date 1
for ₹65,000.
```

This represents one retail sales event.

---

# 4. Grain Definition

The grain defines exactly what one row in the fact table represents.

## Grain

> One row in FACT_SALES represents one product purchased by one customer from one branch on one specific date.

This is the most important design decision in the project.

The grain determines the meaning of every fact-table row and therefore determines how the measures should be interpreted.

Example:

```text
CUSTOMER_ID  = 1
PRODUCT_ID   = 101
BRANCH_ID    = 1
DATE_ID      = 1
QUANTITY     = 1
TOTAL_AMOUNT = 65000
```

This means:

> Customer 1 purchased one unit of Product 101 from Branch 1 on Date 1, generating ₹65,000 in sales.

---

# 5. Why Grain Is Important

Without a clearly defined grain, the meaning of a fact table becomes ambiguous.

For example, if a table contains:

```text
customer_id
product_id
branch_id
date_id
quantity
total_amount
```

we need to know whether one row represents:

- an entire customer order,
- one product within an order,
- one customer visit,
- one transaction,
- or something else.

In this project, the grain explicitly defines the row as:

> One product purchased by one customer from one branch on one date.

Therefore, all measures in FACT_SALES are interpreted at that level.

# 6. Dimensional Modeling Approach

The project uses a **Star Schema**.

The Star Schema consists of:

- One central fact table
- Multiple surrounding dimension tables

The central fact table is:

```text
FACT_SALES
```

The dimensions are:

```text
DIM_CUSTOMER
DIM_PRODUCT
DIM_BRANCH
DIM_DATE
```

The model can be represented as:

```text
                    DIM_CUSTOMER
                         |
                         |
DIM_PRODUCT ------ FACT_SALES ------ DIM_DATE
                         |
                         |
                    DIM_BRANCH
```

The fact table contains the measurable sales events, while the dimension tables provide descriptive context.

---

# 7. Why Star Schema?

The Star Schema was selected because this is an analytical workload.

Business users need to analyze sales from different perspectives:

```text
WHO?
→ Customer

WHAT?
→ Product

WHERE?
→ Branch

WHEN?
→ Date

HOW MANY?
→ Quantity

HOW MUCH?
→ Total Amount
```

The Star Schema makes these analytical questions simple because the fact table contains the measurements and the dimensions provide the context.

For example:

```text
FACT_SALES
    ↓
DIM_PRODUCT
    ↓
GROUP BY CATEGORY
    ↓
SUM(TOTAL_AMOUNT)
```

allows the business to calculate category-wise revenue.

Similarly:

```text
FACT_SALES
    ↓
DIM_DATE
    ↓
GROUP BY MONTH
    ↓
SUM(TOTAL_AMOUNT)
```

provides monthly revenue.

# 27. Foreign Key Constraints

The project defines the relationships using foreign-key constraints.

Example:

```sql
CONSTRAINT FK_SALES_DATE
    FOREIGN KEY (DATE_ID)
    REFERENCES DIM_DATE(DATE_ID)
```

This means:

- `CONSTRAINT` defines a database rule.
- `FK_SALES_DATE` is the name of the rule.
- `FOREIGN KEY` identifies the column as a foreign key.
- `(DATE_ID)` is the foreign-key column in `FACT_SALES`.
- `REFERENCES` specifies the referenced table.
- `DIM_DATE(DATE_ID)` is the referenced key.

Conceptually:

```text
FACT_SALES.DATE_ID
        |
        | FK
        ↓
DIM_DATE.DATE_ID
        |
        | PK
```

# 28. Measures

The fact table contains two main measures.

| Measure | Type |
|---|---|
| Quantity | Additive |
| Total Amount | Additive |

---

# 29. Quantity

`QUANTITY` represents the number of units sold.

Example:

```text
QUANTITY = 3
```

means three units were sold in that fact row.

Because quantity can be summed across customers, products, branches, and dates, it is an additive measure.

Example:

```text
Customer A → 3 units
Customer B → 5 units
Customer C → 2 units

Total = 10 units
```

---

# 30. Total Amount

`TOTAL_AMOUNT` represents the revenue generated by the sales event.

Example:

```text
TOTAL_AMOUNT = 65000
```

means the sales event generated ₹65,000.

It is additive because multiple sales amounts can be summed.

Example:

```text
Sale 1 = ₹65,000
Sale 2 = ₹56,000
Sale 3 = ₹42,000

Total Revenue = ₹163,000
```


The `1 : many` relationship exists because:

# 43. Star Schema Join

The complete sales event can be reconstructed by joining FACT_SALES with the dimensions.

```sql
SELECT
    F.SALE_ID,
    C.CUSTOMER_NAME,
    P.PRODUCT_NAME,
    B.BRANCH_NAME,
    D.DATE,
    F.QUANTITY,
    F.TOTAL_AMOUNT
FROM FACT_SALES F
JOIN DIM_CUSTOMER C
    ON F.CUSTOMER_ID = C.CUSTOMER_ID
JOIN DIM_PRODUCT P
    ON F.PRODUCT_ID = P.PRODUCT_ID
JOIN DIM_BRANCH B
    ON F.BRANCH_ID = B.BRANCH_ID
JOIN DIM_DATE D
    ON F.DATE_ID = D.DATE_ID
ORDER BY F.SALE_ID;
```

This combines:

```text
WHO      → Customer
WHAT     → Product
WHERE    → Branch
WHEN     → Date
HOW MANY → Quantity
HOW MUCH → Total Amount
```

# 54. Sales Trend Analysis

A sales trend shows how revenue changes over time.

The required components are:

```text
TIME
+
SALES MEASURE
```

The time information comes from DIM_DATE and the measure comes from FACT_SALES.

Daily sales trend:

```sql
SELECT
    D.DATE,
    SUM(F.TOTAL_AMOUNT) AS DAILY_REVENUE
FROM FACT_SALES F
JOIN DIM_DATE D
    ON F.DATE_ID = D.DATE_ID
GROUP BY D.DATE
ORDER BY D.DATE;
```

The result gives revenue for each date in chronological order.

The dataset contains dates for July 2026, so daily trend analysis is the most meaningful time-trend analysis for this dataset.

```sql
    ON F.CUSTOMER_ID = C.CUSTOMER_ID
GROUP BY C.MEMBERSHIP
ORDER BY REVENUE DESC;
```

This answers:

> Which customer membership segment generates the most revenue?

# 60. Revenue Contribution by Category

Revenue contribution shows how much of total revenue each category represents.

```sql
SELECT
    P.CATEGORY,
    SUM(F.TOTAL_AMOUNT) AS REVENUE,
    ROUND(
        100 * SUM(F.TOTAL_AMOUNT)
        / SUM(SUM(F.TOTAL_AMOUNT)) OVER (),
        2
    ) AS REVENUE_PERCENT
FROM FACT_SALES F
JOIN DIM_PRODUCT P
    ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP BY P.CATEGORY
ORDER BY REVENUE DESC;
```

The calculation is conceptually:

```text
Category Revenue
----------------- × 100
Total Revenue
```

# 61. Weekend vs Weekday Revenue

The date dimension contains `IS_WEEKEND`.

This allows revenue to be compared between weekends and weekdays.

```sql
SELECT
    D.IS_WEEKEND,
    SUM(F.TOTAL_AMOUNT) AS REVENUE
FROM FACT_SALES F
JOIN DIM_DATE D
    ON F.DATE_ID = D.DATE_ID
GROUP BY D.IS_WEEKEND
ORDER BY REVENUE DESC;
```

This demonstrates why calendar attributes are useful in a dimensional model.

# 68. Important Design Decisions

## Why FACT_SALES is the central table

Because the business process being analyzed is retail sales.

The fact table stores the actual sales events.

## Why dimensions are separate

Dimensions contain descriptive information that provides context for the sales events.

```text
Customer → Who?
Product  → What?
Branch   → Where?
Date     → When?
```

## Why IDs are used in FACT_SALES

The fact table uses IDs to reference dimension records:

```text
CUSTOMER_ID
PRODUCT_ID
BRANCH_ID
DATE_ID
```

This keeps the fact table focused on the sales event while the dimensions provide descriptive attributes.

## Why measures are stored in FACT_SALES

Measures quantify the business event.

```text
QUANTITY
TOTAL_AMOUNT
```

They can be aggregated for analytical reporting.

## Why PRICE is in DIM_PRODUCT

`PRICE` is numeric, but being numeric does not automatically make a column a measure.

The important question is:

> Does the value describe the business event, or does it describe the entity?

In this model, `PRICE` is a product attribute, so it is stored in:

```text
DIM_PRODUCT
```

The sales measures are:

```text
QUANTITY
TOTAL_AMOUNT
```

and they belong in:

```text
FACT_SALES
```

# 74. Sales Trend Concept

Sales trend analysis means:

> Analyzing how a sales measure changes over time.

The two required components are:

```text
Time
+
Measure
```

For this project:

```text
Time
→ DIM_DATE.DATE

Measure
→ FACT_SALES.TOTAL_AMOUNT
```

The daily trend query is:

```sql
SELECT
    D.DATE,
    SUM(F.TOTAL_AMOUNT) AS DAILY_REVENUE
FROM FACT_SALES F
JOIN DIM_DATE D
    ON F.DATE_ID = D.DATE_ID
GROUP BY D.DATE
ORDER BY D.DATE;
```

Conceptually:

```text
FACT_SALES
     ↓
JOIN DIM_DATE
     ↓
GROUP BY DATE
     ↓
SUM(TOTAL_AMOUNT)
     ↓
ORDER BY DATE
```

# 75. Difference Between Sales Trend and Sales Growth

## Sales Trend

Answers:

> How are sales changing over time?

Example:

```text
July 1 → ₹100K
July 2 → ₹120K
July 3 → ₹90K
```

## Sales Growth

Answers:

> How much did sales increase or decrease compared with a previous period?

For example:

```text
July 1 → ₹100K
July 2 → ₹120K

Growth = 20%
```

Sales growth normally requires comparing the current period with a previous period.

The project primarily demonstrates sales trend analysis.
